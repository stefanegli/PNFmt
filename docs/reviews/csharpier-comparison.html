The gaps worth pursuing

Priorities and effort below are engineering judgments from source inspection and focused examples, not project estimates or benchmark results.

GapEvidence and practical benefitRecommendation
Better break selection
High value · medium effort		In the switch example, a long expression caused PNFmt to break the short M(int value) parameter list while leaving the expression long. Wrapping is triggered by the containing line, even when the list itself is short. See actual output.Pursue first. Prefer a break that meaningfully shortens the overlong expression; avoid chopping an unrelated short list just because it shares that line.
Broader C# syntax coverage
High value · incremental effort		Collection/array initializers, tuples, ternaries, patterns, query syntax and switch expressions remained 107–158 columns in the probes at an 80-column target. CSharpier broke these to 36–56 columns. Nested supported calls can still wrap inside such constructs.Pursue in stages. Start with collections/initializers and ternary/switch expressions. XML formatting exclusions
High practical value · moderate effort		CSharpier supports node and range ignore comments in XML. PNFmt has whole-file activation and text-preservation rules, but no XML formatting-control comments.Pursue. Support PNFmt-style XML exclusions so users can preserve hand-laid-out fragments without changing XML meaning through xml:space. Specify whether they also block sorting in dedicated XML formatters. Upstream behavior.
Ordinary comment validation
High robustness value · moderate effort		PNFmt’s final C# guard compares token text, directives, inactive text and exclusions. It does not explicitly compare ordinary comment contents. CSharpier’s comparer checks non-whitespace trivia too.Pursue before broader rewrites. Allow intentional header replacement and permitted indentation changes, while detecting unintended comment loss or edits. This is a guardrail gap, not an observed comment-corruption bug. Attributes on text-bearing elements
Medium value · moderate effort		PNFmt preserves the entire subtree when it contains text, including the opening tag. The probe stayed 136 columns; CSharpier wrapped the attributes to 56 columns while keeping the text. The same blanket rule covers XAML text containers. See actual output.Worth a focused extension. Separate opening-tag layout from child-content preservation for ordinary text-bearing elements. Keep attribute values, text, explicit exclusions and existing xml:space guarantees intact.
Single-node C# exclusions
Medium convenience value · moderate effort		CSharpier’s next-node marker avoids enclosing a single statement/member in an off/on pair. PNFmt currently recognizes only exact standalone off/on markers.Useful, but behind XML exclusions. Existing ranges already solve the core need. Coordinate any new marker with header detection and sorting barriers. Upstream behavior.

Differences that do not automatically justify new work

Canonical compaction

CSharpier can collapse an unnecessarily expanded short call; PNFmt retains existing line breaks. Our compact and expanded inputs therefore remain different under PNFmt, while CSharpier produces the same result.

Defer unless one canonical layout is the goal. Both outputs can be stable on a second run. Stability does not imply identical output for all equivalent starting layouts. Compare the short-call example.

Trailing commas and closing delimiters

CSharpier adds trailing commas in supported multiline constructs and often gives closing delimiters their own line. PNFmt preserves comma tokens and typically keeps call/parameter closing delimiters with the last item.

Style choices, not urgent gaps. Trailing-comma cleanup requires an explicit allowance in our token-preservation checks. Upstream comma printer.

Inactive preprocessor branches

CSharpier derives symbol sets and formats additional branches. PNFmt intentionally preserves inactive code; the probe confirmed that distinction.

Defer until conditional-compilation-heavy projects need it. Multiple parses, branch-specific errors and validation make this substantially more complex than adding an ordinary break point. Symbol-set logic.

XML spelling and text whitespace

CSharpier normalizes quotes, spaces around = and empty-tag spacing, and offers strict/ignore text-whitespace modes. PNFmt intentionally retains those spellings in generic XML; the MSBuild serializer already normalizes its own output.

Keep the conservative defaults. Optional tag-spacing normalization could be useful if users request it. Broad text-whitespace normalization is a poor fit for PNFmt’s preservation rules. Whitespace modes.

Raw strings, DTDs and scripts

CSharpier can reindent raw string literals and supports XML containing a DOCTYPE; the simple DOCTYPE probe formatted successfully. PNFmt preserves literal token text and skips DTD-bearing generic XML. Its C# parser uses regular C# 14 rather than script mode.

Demand-driven additions. Preserve current contracts until a real input set warrants the added handling. These restrictions are documented, not accidental omissions. Literal handling.

Editor integration and caching

CSharpier exposes stdin/stdout formatting, persistent server/pipe modes and a content/config/version cache. PNFmt’s CLI is file-based and already limits normal Git runs to changed files.

Start with stdin/stdout if editor integration is next. A server or cache is worth adding only after measuring that workflow. These are delivery features, separate from formatting quality. CLI capabilities.

Retain the current engine. A wholesale CSharpier backend is less compelling now that wrapping exists. PNFmt’s EditorConfig controls, independent cleanup switches, member ordering, file headers, dedicated project/resource formatting and exact-preservation rules remain useful. Borrow selected printer ideas and regression cases; importing the whole engine also imports its formatting policies.

Observed outputs, not just feature lists

Fifteen deliberately selected inputs were run through both CLIs with an 80-column target, four spaces and LF newlines. Optional PNFmt sorting was off. These are gap-focused examples, not a representative scorecard. Expand a case to inspect the exact input and outputs.

Line lengths include indentation. Shorter is not inherently better; the table tests where wrapping can operate. PNFmt skipped the DOCTYPE case with XML001. Second-pass check commands exited 0 for both tools; a skipped PNFmt file does not make that check fail.

Recommended order

  1. Exercise the existing wrapping options on representative files

    Use a width that suits the repository, then inspect diffs. The root configuration currently leaves the new wrapping features disabled.

  2. Improve break selection, then add collections and ternary/switch wrapping

    These changes address visible shortcomings from the probes without committing to a new printing engine or globally reflowing existing layouts.

  3. Add XML exclusion comments and strengthen C# comment validation

    Users gain control, and future formatting changes gain a better preservation check. Keep approved header changes separate from accidental edits.

  4. Allow safe opening-tag wrapping around preserved text

    Useful especially for text-bearing XML and XAML controls. Scope the change tightly and verify that text/value content is unchanged.

  5. Revisit convenience and policy features only with a concrete need

    Single-node C# ignores, trailing commas, compaction, inactive-branch formatting and editor transport are separate choices. They need not block the core improvements.
